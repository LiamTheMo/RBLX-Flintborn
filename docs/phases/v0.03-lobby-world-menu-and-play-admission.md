# v0.03 — Lobby, protected world menu and Play admission

> **Depends on:** v0.02 · **GDD sources:** §1, §2.1, §3.1, §3.3, §29.1, §31 (all), §34.1 Q1–Q5, Q155, Q160, Q161c

## Objective

Make getting into the game loss-free. A player goes from the secure lobby to a public world, waits in that world's protected main menu while it loads, presses **Play**, and only then spawns, at a random valid location away from other players, with their inventory at risk.

## Player-facing result

- A **lobby** with a Deploy flow and a party panel. Party members queue together into the same world.
- Teleporting into a **public world** lands on a full-screen **world main menu** showing loading progress and connection status, and the text "You are safe until you enter the world."
- **Play** unlocks only when loading is complete. Pressing it spawns the character at a random valid point anywhere on the map, with the transition "Entering world — items are now at risk".
- Leaving from the menu, a failed teleport or a spawn failure never loses anything.
- Before deploying, the lobby lists **every unvaulted item that will enter the run**.

## Confirmed rules

- **Risk begins only after successful Play admission** (§1.1 pillar 2, §31.1). Loading, teleporting, the world menu, a pressed-but-unconfirmed Play and a failed spawn are all loss-free.
- **The admission state defines risk, not the place.** Being inside a play-world server is not the same as ActiveRun (§31.2).
- **Pressing Play deploys every unvaulted lobby backpack/hotbar item** (Q155). Only secure-vault items stay behind.
- **Random spawn anywhere on the map** (§3.1, Q33), not forced to the Outer Rim.
- **No spawn protection**, but spawns must be **away from other players** (Q160).
- **30 players per world** as the provisional cap (Q1).
- **A world lives while anyone is in it** and resets completely when empty (Q2).
- **Surviving players may rejoin their running world**; dead players may not (Q4–Q5). The exclusion itself is enforced in v0.07, but the admission check is built here.
- **A dead player regroups by party** (Q161c): the tribe extracts, meets in the lobby, parties up and starts a new run together.
- **Extraction sends players to the separate lobby**, not to the world menu (Q24).
- **Two places in one universe:** a lobby (start place) and a play world (Q163). Code shared by both lives in `src/shared`; each place enables only its own services.

## Systems and modules

| Path | Responsibility |
| --- | --- |
| `src/server/Services/WorldAdmissionService.luau` | The per-player session state machine from GDD §31.2. Owns the transition to ActiveRun |
| `src/server/Services/TravelService.luau` (not `TeleportService`, to avoid confusion with the Roblox service) | Lobby → world and world → lobby teleports with `TeleportOptions` data, retries and failure handling |
| `src/server/Services/MatchmakingService.luau` | Picks or creates a world server for a party, honouring capacity and the dead-player JobId exclusion list |
| `src/server/Services/PartyService.luau` | Lobby parties: invite, accept, leave, leader, queue together |
| `src/server/Services/SpawnService.luau` | Picks a random valid spawn: terrain and hazard checks, minimum distance from living players, retry and fallback |
| `src/server/Services/LoadoutService.luau` | Moves the whole unvaulted lobby backpack/hotbar into a single resumable transit reservation, and rolls it back on failure |
| `src/shared/Admission/SessionStates.luau` | State names and the legal-transition table, shared with specs and the client |
| `src/client/Controllers/WorldMenuController.luau` | World main menu UI: progress, status, Play button, retry/return |
| `src/client/Controllers/LobbyController.luau` | Deploy screen with at-risk item list, party panel |

**Session states (§31.2):**
- `LobbySafe`
- `TeleportPending`
- `StagingLoading`
- `WorldMainMenuReady`
- `PlayRequested`
- `ActiveRun`
- `ExtractionHolding`
- `ExtractionProtected`
- `MaintenancePreserved`
- `Dead`

Only `ActiveRun` and `ExtractionHolding` carry inventory risk. Every later loss rule must ask `WorldAdmissionService.IsAtRisk(player)` rather than infer it.

**Character spawning:** set `Players.CharacterAutoLoads = false` in the world place. The server calls `LoadCharacter` only after Play is validated. The character stays unable to take damage until initialisation finishes. Then the server commits `ActiveRun` and the transit reservation becomes the run inventory, all in one step.

## Data and persistence

- `profile.transit`: `{ reservationId, items, createdAt, destinationJobId, status }`. Created in the lobby before teleport, consumed exactly once on successful Play, rolled back to the lobby backpack on failure or menu exit.
- Teleport data carries `reservationId` and `partyId` only. Never item data the client could edit.
- **World-place configuration:** make the play-world place joinable only through server teleports within the universe (§34.1). Use a per-JobId death exclusion list in matchmaking and in world admission.

## Security and anti-exploit

- A duplicate Play click or forged remote produces exactly one spawn (idempotent on `reservationId`).
- The client's "loaded" flag is a hint. The server checks profile, world readiness and lease itself.
- A kill attempt on a pending character does nothing. CombatService (v0.06) must reject damage to non-ActiveRun players.
- Once ActiveRun begins, a client-initiated teleport or exit is an ordinary departure (corpse rules in v0.07), not a safe exit.

## UX and accessibility

- The world menu is the first thing seen in every world join, including rejoins.
- The Play button is large, focusable on controller and touch, and disabled with a clear reason while loading.
- Failure screens offer retry and return-to-lobby without losing anything.
- The deploy list shows each at-risk item with icon and text, plus a reminder to vault items first.

## Validation

**Automated specs:**
- the state machine allows only §31.2 transitions;
- only ActiveRun and ExtractionHolding report at-risk;
- spawn selection rejects candidates within the minimum distance of players and hazards;
- reservation consume and rollback is exactly once.

**Studio and live checks (§31.7 P0 acceptance tests):**
- Join the world 100+ times with delayed loading: no vulnerable character before Play.
- Simulate teleport failure, network loss, character-load failure, profile timeout and a kick from the menu: identical safe inventory, no corpse.
- Inject double Play and spoofed remotes: one ActiveRun only.
- Quit after ActiveRun begins: an ordinary departure is recorded. The corpse itself arrives in v0.07.
- Two parties queue at once: each lands together, and nobody spawns within the minimum distance of another player.

## Exit criteria

- [ ] Separate lobby place and world place exist (two places confirmed, Q163), and the deploy job publishes to both (done in v0.01: the lobby through `ROBLOX_LOBBY_PLACE_ID`, the play map through `ROBLOX_MAIN_PLACE_ID`). Each place starts only its own services.
- [ ] Session state machine enforced server-side, and all §31.5 failure cases are loss-free.
- [ ] Party queue delivers a party into one world.
- [ ] Random spawn honours the minimum distance with no spawn protection.
- [ ] Deploy screen lists every item about to be put at risk.
