# v0.02 — Player data, persistence and session safety

> **Depends on:** v0.01 · **GDD sources:** §12.3, §22.3, §23.1–23.3, §24, §34.2 non-duplication policy, §40.2

## Objective

Build the persistence layer every later system writes through: a versioned player profile, a session lease that stops two servers owning the same account, an operation journal that makes every grant and charge happen exactly once, and DataStore handling that never reports a failed save as a success.

## Player-facing result

Mostly invisible. A tester can:

- join, have a profile created, leave and rejoin with the same data;
- see a "Saving…/Saved/Save pending" indicator for their profile;
- join a second server while the first still holds their lease, and be held safely until the lease is released or expires, rather than loading stale data.

## Confirmed rules

- **Vaulted items, currencies, XP, levels, masteries and perks persist forever** across world resets (§2.2, Q3). Nothing in this layer may wipe them.
- **The lobby backpack is durable** across logout, reconnect, lobby server changes and world resets (Q152).
- **Every unique item instance exists in exactly one place with one owner** (§12.2 invariant 3, §22.1). This includes tradeable Permanent items.
- **Retries never duplicate or double-charge** (§12.2 invariant 4, §23.3).
- **XP and mastery progress save as earned**, including during a run that ends in death (Q70).
- **Coins and Gems never drop** and are account balances, not inventory (Q94).

## Data and persistence

- **Key:** one profile key per `UserId` (`Profile_<UserId>`) in a single profile DataStore. Writes use `UpdateAsync` so the revision and lease are checked inside the update callback.
- **Session lease:** written on load with the server's `JobId` and an expiry (placeholder 5 minutes, renewed every autosave). Another server may take over only after expiry or an explicit release. A server that loses its lease stops writing immediately.
- **Stale writes:** every save compares `profileRevision`. A write from an older revision is rejected and logged (§22.3).
- **Autosave:** on an interval, on important commits (operation committed) and on `PlayerRemoving`/`BindToClose`. Shutdown saves run within Roblox's close budget.
- **Operation journal:** every grant, charge or transfer in later phases calls `OperationJournal.Run(profile, operationId, fn)`. If the ID is already committed it returns the stored result; if pending it reconciles; otherwise it applies once. The journal is trimmed with a retention limit to respect DataStore size budgets (§23.2).
- **Instance IDs:** `HttpService:GenerateGUID(false)` on the server only. Clients never submit IDs that create items.

## Security and anti-exploit

Abuse cases from GDD §24 this phase must close:

- Two devices or servers acting on one account: lease plus revision checks.
- The same request repeated through lag or macros: idempotency keys.
- Client-submitted quantities or IDs: never trusted. Clients send intent only.
- DataStore throttling or shutdown: operations stay `pending`, never marked successful early.
- Negative or overflowing quantities: positive bounded integers only.

## UX and accessibility

- A small persistent save indicator with text plus an icon, never colour alone.
- If a profile cannot load, show a clear retry screen. Never drop the player into the game with a blank profile.

## Validation

**Automated specs (`tests/luau`):**
- schema defaults are complete;
- every migration step upgrades an older fixture to the current version without losing fields;
- `OperationJournal` returns the same result for a repeated ID and never re-applies a committed operation;
- revision comparison rejects stale writes;
- quantity validation rejects negative, fractional and oversized values.

**Studio checks:**
- Join, change a test field, leave, rejoin: the value persists.
- Join two Studio test servers with the same account (Team Test): the second waits for the lease.
- Simulate DataStore failure (mock gateway that errors): the status shows pending and nothing is reported as saved.
- Shut down a server with `BindToClose`: the final save commits.

## Exit criteria

- [ ] Profiles load, save, migrate and release with a lease.
- [ ] Stale and concurrent writes are rejected in tests.
- [ ] Operation journal used for a sample grant with exactly-once behaviour proven by specs.
- [ ] Save status visible to the player.
- [ ] No other module calls DataStore APIs directly.

No gameplay inventory, vault UI, currency sources or extraction yet. This phase only provides the safe storage and transaction primitives they will use. Cross-server item trading arrives in v0.14.
